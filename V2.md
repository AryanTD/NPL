# NPL v2 — High-Level Roadmap

## Context

v1 works: a real-time multiplayer auction with algorithmic bots, deployed on Vercel + Render + Neon. v2 has two goals, set by the user:

1. **Get real users** — Nepali cricket fans actually playing the game.
2. **Serve as portfolio evidence** for a software engineering job.

These converge on one outcome: *a live, reliable product with real traffic, whose engineering decisions can be explained in an interview*. They diverge on feature count — more features serve neither goal much, so this roadmap is deliberately short.

**Deadline:** launch before NPL season (assumed Nov–Dec, ~2 months out). That window is when Nepali cricket fans are most primed to care, so distribution must be ready *before* it, not during.

**Decisions already taken:**
- All four workstreams are in scope: foundation, endgame, reliability, share loop.
- Crash recovery is **out**. Reliability stays at *prevention* (keep the server warm, don't let lobbies get stuck) rather than *recovery* (persist and rehydrate in-flight auctions). Restarts killing live auctions is accepted for now.
- Bots stay algorithmic. The decision engine is better engineering and better economics than an LLM call per bid — docs should be corrected to match, not the code.

**Working agreement:** these topics get picked off one at a time, in order. Each one gets its own detailed design discussion before any code is written.

## Topic 1 — Rescue the lost migrations

**Effort:** ~30 min · **Depends on:** nothing · **Blocks:** Topic 3

`.gitignore` ignores `apps/server/prisma/migrations/`. Eight migrations exist only on this laptop — a fresh clone cannot reproduce the schema, and CI can never run `prisma migrate deploy`.

- Fill the gaps in `apps/server/.env.example` (missing `DIRECT_URL`), add one for `apps/web`

**To resolve when we get here:** whether the committed migration history is internally consistent, or needs a squash.

## Topic 2 — Reliability: keep warm, stay unstuck

**Effort:** ~half day · **Depends on:** nothing

Two live user-facing problems. Render free tier sleeps, so a first-time visitor hits a ~50s cold start. And when the server restarts, `auctionEngine.ts` leaves the lobby stuck in `AUCTION` status forever, which then blocks that user from creating a *new* lobby.

- External uptime pinger against `/health` (Vercel Hobby cron only fires daily — won't work)
- Auto-reset or expire lobbies stranded in `AUCTION`
- Harden shutdown with a force-exit fallback

**To resolve when we get here:** which pinger; whether stale lobbies expire on a timer, on boot, or on the user's next create attempt.

## Topic 3 — Repo credibility: README, CI, doc cleanup

**Effort:** ~1 day · **Depends on:** Topic 1

The cheapest credibility available for the job goal. There is no root README, the web one is untouched `create-next-app` boilerplate, and there's no CI of any kind despite PRs being in use.

- Root README: what it is, architecture diagram, local setup, the interesting engineering decisions
- GitHub Actions: typecheck + test + build on PR (note `prisma generate` must run first)
- Delete or correct stale docs — `railway.toml`, `design/README.md` (still references Clerk), `ROADMAP.md`, `TASKS.md`
- Correct CLAUDE.md where it claims Claude-powered bots and lists a deleted file

**To resolve when we get here:** how much of CLAUDE.md becomes the public README vs stays internal.

## Topic 4 — Tests for the auction engine

**Effort:** ~1–2 days · **Depends on:** Topic 3

The auction engine is the strongest thing in this codebase and has zero test coverage. The only existing tests cover `decideBid`. This is the gap a reviewer notices first.

- Bid validation: affordability, quota exhaustion, the reserve-for-remaining-slots rule
- Phase transitions and the unsold-round eligibility filter
- Lucky draw contender selection
- Strategy for the DB dependency — the engine is not currently a pure function

**To resolve when we get here:** whether to extract pure logic for testability or test against a real test database.

---

## Topic 5 — Squad rating engine

**Effort:** ~1 day · **Depends on:** nothing (but gates 6, 7, 8)

The game currently *stops*; it doesn't *end*. A score at auction close gives a winner, a loser, and a reason to play again — without waiting on real NPL matches.

- Scoring inputs: player quality, value-for-money against category max, role balance, purse efficiency
- Computed server-side at completion, where all squad data is already in memory
- `Player.quality` exists in the DB but is not on the shared `Player` type — needs plumbing

**To resolve when we get here:** the actual formula and its weights; whether the rating is a single number, a letter grade, or a breakdown across dimensions.

---

## Topic 6 — Persisted, addressable results

**Effort:** ~1 day · **Depends on:** Topic 5

Today the results screen is pure client state from one socket payload — refresh and it's gone. Nothing can be linked to or shared, which blocks the entire growth loop.

- A results route that survives refresh and can be opened by anyone
- Decide the storage shape: recompute from existing tables, or store the computed rating
- Auction history for signed-in users falls out of this nearly for free

**To resolve when we get here:** whether results live on the Next.js side reading Prisma directly (like the players page) or behind the Express API.

---

## Topic 7 — Endgame screen upgrade

**Effort:** ~1 day · **Depends on:** Topics 5, 6

`AuctionCompleteScreen` already renders all eight squads. It has no score, no ranking, no comparison, and no way out — the user is stranded with only footer links.

- Rank the eight teams by rating, highlight the winner and the user's finish
- Score breakdown: where points were won and lost
- Play-again and exit routes out of the screen

**To resolve when we get here:** how much motion and reveal ceremony (framer-motion is already installed).

---

## Topic 8 — Share loop

**Effort:** ~1.5 days · **Depends on:** Topic 6

The growth engine. Facebook is the right primary channel for a Nepali audience; WhatsApp matters too.

- Generated squad-card image via `next/og` — note fonts are CDN-linked, so they need fetching or self-hosting at the edge
- Share buttons on the results screen
- Per-route metadata — today every page shares as the generic "NPL Auction" title

**To resolve when we get here:** what the card shows, and whether guests can share (their identity is localStorage-only).

---

## Topic 9 — Launch and distribution

**Effort:** ongoing · **Depends on:** Topics 2, 6, 8

The step that actually decides whether either goal is met. Building it is not launching it.

- Nepali cricket Facebook groups, r/Nepal, cricket Discords
- Instrument enough to know whether anyone is playing and where they drop off
- Confirm the real NPL season dates and work backwards from them

**To resolve when we get here:** analytics choice, and how much to seed manually vs let spread.

---

## Explicitly deferred

Chat, public matchmaking rooms, stranger squad ratings, player photos (real-cricketer IP risk — illustrated or generated avatars are the safer path), music, daily challenge, fantasy scoring. Several are good ideas; none earn a slot before the season launch.

---

## Verification

Each topic carries its own verification, defined when we design it. Repo-wide, v2 is done when:

- A clean clone reproduces the schema and passes CI
- The deployed server answers without a cold start, and a stranded lobby never blocks a new game
- A completed auction produces a ranked result at a URL that survives refresh and renders a share card
- A person who is not the author has played a full auction end to end
